# Acceptance criteria — FitFindr

Five criteria that say what "working" means for this agent, written in unit 3
**before** any results existed.

An acceptance criterion names a target: a number, a count, a rate, or something
a person could plainly observe. *"The agent handles errors"* is an opinion.
*"When search returns nothing, the agent stops before calling the second tool,
in 5 of 5 tries"* is a criterion.

Under each one, write a sentence or two on **why that target** and not a
stricter one. A reason that says something about your tools, your loop, or the
data earns credit; *"80% seemed reasonable"* does not.

> Missing your own targets next unit costs you nothing. Setting a target so
> easy you can't miss it does.

**Two are written for you. You write three.**

---

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three
tool calls and returns a fit card — in at least 4 of 5 tries.

**Why this target:**
Search uses regex extraction and simple keyword matching against listing descriptions. Because natural language queries may use informal phrasings or synonyms not present in the listing text, keyword matching will occasionally miss a valid match. A 4 of 5 target demands high reliability while realistically accommodating lexical mismatch in basic keyword search.

---

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling
`suggest_outfit` and returns a message naming what to change — 5 of 5 tries.

**Why this target:**
This path is controlled entirely by deterministic Python branching logic (`if not session["search_results"]`), not an LLM. When search yields an empty list, halting and populating `session["error"]` with actionable suggestions should succeed 100% of the time without variance.

---

## 3. Something about state

Given a successful query where `search_listings` returns at least one result, `session["selected_item"]["id"]` matches `session["search_results"][0]["id"]`, and that exact listing dictionary is passed into both `suggest_outfit` and `create_fit_card` without field corruption or loss — 5 of 5 tries.

**Why this target:**
State propagation through the `session` dictionary is deterministic Python reference passing. Once the agent chooses the top listing from search results, that object must reliably flow through downstream tools with zero dropped keys or state mutations.

---

## 4. Something about the fit card

Given 5 runs across different matching listings, the generated fit card in `session["fit_card"]` explicitly mentions the item's platform and price, contains between 2 and 4 sentences, and shares no identical opening sentence across the 5 listings — in at least 4 of 5 tries.

**Why this target:**
The fit card is generated by an LLM prompt requiring key factual metadata (platform and price) and length constraints suitable for social media captions. With temperature set above zero, captions should exhibit stylistic variety across distinct items. A 4 of 5 target accounts for minor generative variance where the model might occasionally omit a platform name or join sentences.

---

## 5. Your choice

Given a matching query run against an empty wardrobe (`wardrobe["items"] == []`), the agent completes all three tool calls, and `suggest_outfit` returns non-empty styling advice without crashing or referencing non-existent wardrobe item IDs (`w_...`) — in at least 4 of 5 tries.

**Why this target:**
New users will frequently start with an empty wardrobe. The system must degrade gracefully to general silhouette and styling advice rather than failing or raising an exception. Because the LLM produces the advice, 4 of 5 allows for occasional prompt non-compliance regarding references to owned items.
